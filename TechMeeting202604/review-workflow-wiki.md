# Issue から始める開発、レビューワークフローでチームのメンタルモデルを洗練する

チームのコミュニケーションによるメンタルモデルの洗練を重視し、AI 時代において人間に求められる**判断力**を身につけられる仕組みを作った。

---

## 1. 解決したい課題

### メンタルモデル不在のコード

Peter Naur は「プログラムの本質はソースコードにはない。プログラマの頭の中にある"理論"、すなわちメンタルモデルこそが本体だ」と述べている（参考: [コードレビューとは何か](https://zenn.dev/baleenstudio/articles/what-is-a-code-review)）。

コードレビューの本質は「バグ探し」ではない。研究によると、レビューコメントのわずか 14% しかバグに関連していない。真の目的は、**コードが体現する設計判断とその影響をチームで共有する営み**である。

チームでは、ある日 BE のコアメンバーが別チームに引き抜かれ、以下の問題が顕在化した。

- **設計意図の喪失** — どのような取捨選択をして今のコードに至ったのか、説明できる人がいなくなる
- **仕様境界の不明瞭化** — どのような機能が存在し、何が意図的に「無い」のかがわからなくなる
- **影響範囲の不可視化** — 変更がどこまで波及するか判断できず、安全な変更が困難になる

AI が生成するコードは完成が早いが、人間がそのコードのメンタルモデルを持たなければ、**コードベースは成長を止める**。

### 判断能力の喪失

Brian Cantwell Smith の枠組みに基づき、知的作業を2つに分離して考える。

| | 判断（Judgment） | 演算（Reckoning） |
|---|---|---|
| **定義** | 何を問うか、何を決めるか、責任を取ること | 与えられた条件の中で広く計算すること |
| **特徴** | 直感が先にあり、後から言語化する | 適切なコンテキストがあれば自動化できる |
| **担い手** | 人間（AI 時代でも不変） | AI に委譲可能 |

**問題**: 従来は若手が「演算」（労力のかかる作業）を担当し、その過程で現実との摩擦を経験して判断力を養っていた。AI に演算を全面委譲すると、**判断力が育つ機会を失う**。

- 成長とは、**具体的行動の繰り返し → 現実との摩擦 → 言語化以前の直感の醸成**
- 短い言語トークンに多くの情報を詰められるようになることが「上達」
  - 例: 「冪等性」の一語に「安全な再実行」「並列実行適性」「設計の単純化」など複数の含意がある
- HITL（Human-In-The-Loop）は時代遅れではない — **能力拡張が必要な場面では必須**

だから、レビュープロセスの中に**判断の機会を明示的に設計する**必要がある。

## 2. 何を作ったのか

Claude Code のスキル・エージェント機構を活用した、**AI マルチエージェントコードレビューワークフロー**を構築した。

### システム概要

以下の図は、6 つのスキルの関係と、Author / Reviewer のワークフローを示す。

<!-- review-system-overview.drawio の画像をここに差し込む -->
![レビューワークフロー概要](review-system-overview.drawio.png)

**核心的な設計**:

- **セルフレビュー → ピアレビュー** の2段階構成
- Author の判断記録（意思決定フェーズ）が PR Body に埋め込まれ、Reviewer はそれを参照してフィルタリングする
- Author が「既に検討済みの指摘」を明示することで、Reviewer は未検討の論点に集中できる

### システム詳細

以下の図は、レビュー系 skill / shell が **何を input にし、何を output として Workspace や GitHub に渡すのか** を含めた詳細フローを示す。

<!-- review-system-detail.drawio の画像をここに差し込む -->
![レビューシステム詳細構成](review-system-detail.drawio.png)

**この図で読み取れること**:

- `/self-review` は **仕様コンテキスト + diff** を input にし、`decisions.md` と `self-review-report.md` を output する
- `/peer-review` は **PR body + shared workspace** を input にし、`selected-comments.md/.json` と `peer-review-report.md` を output する
- `workspace-init.ps1` / `collect-diff-stats.ps1` / `partition-diff.ps1` / `post-review.ps1` は、それぞれ **box 内に input / output を明記** している
- 右側の Workspace 一覧で、各 artifact について **誰が保存し、次に誰が読むか** を追える
- `decisions.md → PR body → peer-review → selected-comments.json → /post-review`

---

### 各スキルの解説

#### `/self-review` — セルフレビュー（Author 用）

PR 著者が、コードを push する前に自分のコードを包括的にレビューするスキル。

**核心: 意思決定フェーズ**

AI エージェントが生成した指摘事項に対し、著者が一つ一つ判断を記録する。

| ステータス | 意味 | レビュアーへの影響 |
|---|---|---|
| ✅ fix | 修正する | スキップ |
| 📋 maintain | 理由を記録し、現状を維持する | 理由を確認 |
| 💬 defer | 後日対応にする | 認識の共有 |
| 🚫 reject | 指摘が不要と判断 | 妥当か質問 |

この記録が PR Body に埋め込まれ、ピアレビュー時の自動フィルタリングに使われる。

**ワークフロー**:
1. ワークスペース初期化
2. 仕様コンテキスト収集（Issue / Redmine / PR）
3. diff 統計・技術スタック検出
4. diff の FE/BE 分割
5. 6〜9 エージェントによる並列分析
6. 指摘事項の統合・検証（重複排除、信頼度フィルタ）
7. **意思決定フェーズ** — 人間が各指摘に判断を下す
8. レポート生成・保存

<!-- /self-review の使用例スクリーンショットをここに差し込む -->

#### `/peer-review` — ピアレビュー（Reviewer 用）

レビュアーが PR を理解し、フィルタリングされた分析結果を元にレビューするスキル。

**セルフレビューとの違い**:
- **トーン**: 断定的 → 質問形式（「〜ではないでしょうか？」）
- **エージェント数**: フルセット → プリセット選択（core / standard / full）
- **フィルタリング**: セルフレビュー記録に基づき、既検討の指摘を自動除外

**プリセット**:

| プリセット | エージェント数 | 用途 |
|---|---|---|
| core（デフォルト） | 2〜3 | 素早いレビュー（bug + spec） |
| standard | 4〜6 | 通常のレビュー（+ security + simple） |
| full | 6〜9 | 包括的レビュー（全エージェント） |

<!-- /peer-review の使用例スクリーンショットをここに差し込む -->

#### `/diff-navigator` — 差分ナビゲーター

変更の「なぜ」を先に示す、意図優先のガイドツアーを生成するスキル。

**3 層出力**:
1. **Layer 1**: エグゼクティブサマリ（1 段落）
2. **Layer 2**: 変更グループ（ファイルパスではなく関心事でグルーピング）
3. **Layer 3**: ファイルレベル詳細（行アンカー付き）

レビュアーが PR の全体像を素早く把握するために使う。ピアレビューの前段として有効。

<!-- /diff-navigator の使用例スクリーンショットをここに差し込む -->

#### `/draft-pr` — PR 作成

Issue / Redmine のコンテキストと diff を分析し、PR を作成するスキル。

- セルフレビュー記録が存在する場合、PR Body に自動埋め込み
- Issue / Redmine から PR タイトルを自動生成
- 技術スタックに応じたチェックリストを自動選択（FE / BE）
- `gh pr create --draft` でドラフト PR として作成

<!-- /draft-pr の使用例スクリーンショットをここに差し込む -->

#### `/edit-pr` — PR 編集

既存 PR の Body をセクション単位で更新するスキル。

- 対応内容の更新（diff 再分析）
- チェックリストの更新（技術スタック変更時）
- セルフレビュー記録の追加・更新
- Redmine チケットの追加
- 全セクション一括編集

#### `/post-review` — レビュー投稿

ピアレビューやセルフレビューの結果を GitHub PR に Pending Review として投稿するスキル。

- 指摘をライン単位コメントと全般コメントに分類
- 重要度に応じたプレフィックスを自動付与:
  - `[must]`: 必須修正（セキュリティ、バグ、設計問題）
  - `[ask]`: 質問・確認
  - `[imo]`: 個人的意見
  - `[nits]`: 軽微な指摘
  - `[fyi]`: 参考情報
- **Pending Review**（著者にのみ表示）として作成 → 手動で Submit

## 3. どう使われるか

### 日常ワークフロー

以下の図は、Author と Reviewer の日常的なワークフローと、各ステップで人間の判断と AI の演算がどう分担されるかを示す。

<!-- review-usecase-flow.drawio の画像をここに差し込む -->
![ユースケースフロー](review-usecase-flow.drawio.png)

**Author の 1 日**:
1. Issue / Redmine チケットを確認し、仕様を理解する（**判断**）
2. 実装する（**判断** + 演算）
3. `/self-review` を実行 → AI が指摘事項を生成（演算）
4. 各指摘に対して fix / maintain / defer / reject を判断する（**判断**）
5. `/draft-pr` で PR を作成し push（演算）

**Reviewer の 1 日**:
1. PR のレビュー依頼を受信する
2. `/diff-navigator` で変更の全体像を把握する（演算 → **理解**）
3. `/peer-review` を実行 → AI がフィルタリング済みの分析を生成（演算）
4. 投稿する指摘を選択し、プレフィックスを付ける（**判断**）
5. `/post-review` で Pending Review として投稿 → 手動 Submit（**判断**）

### どう課題を解決しているか

#### セルフレビューの意思決定フェーズ → 判断の明示的記録

AI が指摘事項を生成した後、著者が各指摘に対して **fix / maintain / defer / reject の判断を記録する**。これは「AI に言われたからそうしました」ではなく、**自分の判断として設計意図を言語化する行為**。

- 判断を記録する過程で、著者はコードの設計意図・トレードオフを改めて言語化する
- この言語化こそが「メンタルモデルの強化」であり、判断力の訓練になる
- 記録は PR Body に残るため、将来のメンテナーも設計判断の経緯を追える

#### ピアレビューの自動フィルタリング → レビューコスト削減

Reviewer は Author が既に検討した指摘を再確認する必要がない。

- ✅ fix 済み → スキップ（既に修正されている）
- 📋 maintain → 理由を確認（設計判断として妥当か検証）
- 🚫 reject → 妥当性を質問（見落としの可能性を確認）

これにより、Reviewer は**未検討の論点と、著者の判断の妥当性検証**に集中でき、レビュー全体の効率が上がる。

#### Issue 起点の開発 → 仕様と実装の一貫性

`/self-review` と `/peer-review` は Issue / Redmine から仕様コンテキストを自動収集し、エージェントに渡す。`spec-reviewer` エージェントが仕様と実装の整合性を検証する。

この仕組みにより:
- Issue を充実させようという動機が自然に生まれる
- 実装前に Issue でチームの方向性をすり合わせる文化が醸成される
- 「仕様→実装→レビュー」の一貫性が保たれる

#### エージェントのスコープ分離 → 確認観点の言語化と品質安定

9 つのエージェントはそれぞれ異なる観点（バグ・セキュリティ・パフォーマンス・設計・命名・仕様整合性）で分析する。各エージェントの「何を確認するか」は `.claude/agents/` 配下のプロンプトに言語化されている。

- 観点が明文化されているので、レビューの質がまちまちにならない
- AI の確率的出力に対してガードレール（スコープ分離、信頼度フィルタ、重複排除）を設けている
- 観点を追加・改善するには、エージェントプロンプトを更新するだけでよい

---

## 効果

- **レビューへの抵抗感が減少** — スキルを実行することから始められるので、手順が明確
- **確認内容の理解度が向上** — 指摘に対して判断を記録する過程で、コードへの理解が深まる
- **Issue 起点の文化が醸成** — Issue を充実させ、実装前にチームですり合わせる動機が生まれた
- **観点の言語化による品質安定** — 大量チェックの形骸化を AI で解決し、人間は判断に集中

## 今後の展望

- Redmine → GitHub Issue → コード → Wiki の一つながりのパイプライン
- GitHub Agent による不整合の常時ガーデニング（Wiki 未更新の検知など）
- エージェントプロンプトの継続的改善とチーム固有の観点の蓄積
