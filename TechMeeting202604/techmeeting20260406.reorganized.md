# テックミーティング発表内容（再整理版）

## はじめに

- 品質管理クラウドチームでの AI エージェント（Claude Code / Copilot CLI）活用について話す
- 単なる「便利ツール紹介」ではなく、**AI時代に仕事をどう設計するか** がテーマ
- 枠組み: **Brian Cantwell Smith** の「**Reckoning**（演算）」と「**Judgment**（判断）」
    - Smith は **計算の哲学・AI哲学・認知科学** を横断する研究者（1950–2025）
        - MIT で博士号を取得し、世界初のリフレクティブ（自己反映型）プログラミング言語 **3-Lisp** を開発
        - Stanford 大学で **CSLI（言語情報研究センター）** を共同設立し、言語・計算・哲学の学際研究を牽引
        - **Computer Professionals for Social Responsibility（CPSR）** の初代会長として、テクノロジーの社会的責任を早くから提唱
        - トロント大学情報学部の学部長を務め、同学部を世界的な iSchool へ変革。晩年は **Reid Hoffman Chair in Artificial Intelligence and the Human** を保持
        - 主著に *On the Origin of Objects*（1996）、***The Promise of Artificial Intelligence: Reckoning and Judgment***（2019, MIT Press）など
    - LinkedIn 共同創業者 **Reid Hoffman** は Stanford 時代に Smith の「AIの哲学」講義を受け、深い影響を受けた人物の一人
        - Hoffman は後にトロント大学へ **245万ドルの寄付** を行い、Smith の名を冠した寄附講座を設立した
        - HCI/AI 分野の権威 **Terry Winograd**（Stanford）も Smith と長年にわたる学術的対話を行った協力者として知られる
    - この発表では、Smith の議論を開発実務向けにややラフに使う
    - Judgment = 何を問うか・何を採るかを引き受けること
    - Reckoning = 与えられた条件で広く計算すること
    - 少なくとも現行の LLM の得意領域は Reckoning である
    - ただし、人間が与えた判断基準に沿って演算させることはできる
- 本日の主張: **仕事を「判断」と「演算」に分離し、そのループを回す仕組みを設計しよう**
    - 決定→演算→決定→演算
    - 2つの事例を通じてこのパターンを見ていく
    - 特にレビューでは、「いまこの変更を採るか」と「将来その判断を担える人を増やすか」を分けて考える必要がある

### 今日話すこと — 全体像

品質管理クラウドチームで、AIエージェントを活用して **2つの仕組み** を作った。

```
┌─────────────────────────────────┐    ┌─────────────────────────────────┐
│  事例1: ドキュメントパイプライン  │    │  事例2: AIレビューワークフロー    │
│                                 │    │                                 │
│  Git上のMarkdown（193ファイル）   │    │  Claude Codeのスキル/エージェント │
│       ↕ 自動同期                │    │       ↕ 構造化レビュー           │
│  社内Wiki（GROWI）              │    │  GitHub PR                      │
│                                 │    │                                 │
│  「成果物の作り方」を設計した     │    │  「判断の仕方」を構造化した       │
└─────────────────────────────────┘    └─────────────────────────────────┘
```

- 事例1は **「ドキュメントが腐る」問題** を解決するためのインフラ
    - Git を SSOT にし、Wiki との同期を自動化する CLI + GitHub Actions
- 事例2は **「AIレビューだけでは成長しない」問題** を解決するための仕組み
    - 9つの専門エージェントが分析し、人間が意思決定を記録するワークフロー
    - 目の前のPRを判断しつつ、判断力そのものも育てる
- どちらも「人間が判断の枠組みを作り、AIが演算を担う」パターンで設計されている

## 事例1: ドキュメントパイプライン — 「作り方を作る」

> 趣旨: 仕事のやり方を設計しよう・作り方を作ろう
> — つまり、何を自動化するかという**判断**と、実際の構築・運用という**演算**を分けて設計する

### 課題 — なぜ作ろうと思ったか

- 実装とWikiが一致しない（ドキュメントが腐る）のは常に課題
- コードをSSOT（Single Source of Truth）にしたいが、他部門との連携では Wiki が必要
- Issueにも仕様を書いて、Redmineにも仕様を書いて、実装して、Wikiにも反映して → どこかで整合しなくなる
    - 同じことを2回も3回も書くことをなくしたい
    - それぞれ役割があるから（現状）なくせない
    - GithubもRedmineもGrowiもAPIがあるから、連携を簡単にする方向で進める

### 判断: 何を作るか決める（Judgment）

- **Wikiをローカル（Git）で管理すれば何が可能になるか？** ← これが「問い」
    - コーディングエージェントはローカル情報に最も効率よくアクセスできる
    - Wikiを読んで既存仕様との整合性をチェックできる
    - Wikiをコードから生成させることができる
    - Git管理にすれば GitHub Actions に組み込める

- **技術的課題に対する意思決定:**

| 課題 | 判断 | 根拠 |
|------|------|------|
| Growiは社内ネットワークのみ | selfhostランナーで解決 | Claude Code Action はselfhostランナー対応 |
| Git画像管理でリポジトリが重い | Azure Blobストレージ | 保存量単価 約¥2.8/GB、転送量 月100GBまで無料（10GBで月30円未満） |
| Blobへの手順がめんどい | CLIスクリプト + VSCodeタスク | 5案を評価し拡張性で選択（image-upload-evaluation.md） |
| 既存Wikiからの移行 | 過渡期運用 + API取り込み | 画像は自動でBlobに配置する仕組みに |
| CLI設計方針 | ユースケース駆動に再設計 | 「CodingAgentが一貫して実装・保守しやすい構成にする」 |

- これらの判断は meta/ 配下にドキュメントとして残している
    - sync-plan.md、growi-tooling-migration-plan.md、image-upload-evaluation.md

### 演算: AIに作らせる（Reckoning）

#### 作ったもの: ドキュメント管理リポジトリ

```
kscloud-quality-concrete-docs/
├── docs/           ← 仕様ドキュメント本体（193ファイル、GROWI同期対象）
│   ├── products/kscloud/quality-concrete-cloud/
│   │   ├── specification.md          ← frontmatter で GROWI パスを指定
│   │   ├── dashboard/
│   │   └── ...
│   └── （バージョン別: ver1.01.00 〜 ver202606xx）
├── meta/           ← 設計メモ・判断の記録
│   ├── sync-plan.md                  ← 同期パイプライン設計
│   ├── growi-tooling-migration-plan.md ← CLI再設計計画
│   └── image-upload-evaluation.md    ← 画像方式5案の評価
├── tools/          ← growi-docs CLI（TypeScript）
│   ├── growi-docs.ts                 ← ルーター
│   └── growi-docs/
│       ├── commands/  （6コマンド）
│       └── lib/       （9ユーティリティ）
└── .github/workflows/
    ├── docs-validate.yml   ← PR/push時にバリデーション
    └── sync-to-growi.yml   ← release push で差分同期
```

- 各 Markdown に **frontmatter** でメタデータを持たせる（設定ファイル不要）

```yaml
---
growi_path: /製品/KsCloud/品質管理クラウド/仕様（Git）/ダッシュボード/打設スケジュール
title: 打設スケジュール
sync: true
---
```

#### 作ったもの: growi-docs CLI

Claude Codeで構築した統合CLIツール。ユースケース駆動で設計。

| コマンド | 機能 |
|----------|------|
| `docs:check` | frontmatter検証、パス重複チェック、GROWI許可ルートの確認 |
| `docs:publish` | Git→GROWI同期（`--file` 単体 / `--files-file` 一括 / `--dry-run`） |
| `docs:import:page` | GROWI→Git取り込み（画像をBlobストレージに自動移行） |
| `docs:import:tree` | GROWIツリー一括取り込み（source-root / target-root 指定可） |
| `docs:image:paste` | クリップボード画像→Azure Blob→Markdownリンクをクリップボードへ |
| `docs:image:upload` | ローカル画像ファイル→Azure Blob |
| `fix-permalinks` | GROWI ID型リンク→パス型URL変換 + 旧パス一括書換え |

- 画像貼り付けはVSCodeショートカット（`Ctrl+Alt+V`）で完結

#### 作ったもの: 自動同期パイプライン

```
 開発者が docs/ を編集
     ↓
 PR作成 → docs-validate.yml が自動実行
     │     ・TypeScript型チェック (tsc --noEmit)
     │     ・frontmatter/パス整合性チェック (docs:check)
     ↓
 release ブランチへマージ
     ↓
 sync-to-growi.yml が自動実行
     ・git diff で変更 Markdown を検出
     ・growi_path の変更を検知 → 事故防止（変更があればfail）
     ・変更ファイルのみを GROWI に publish
     ・変更なしなら zero-diff skip
```

- **冪等な設計**: 再実行しても安全。画像はBlob上のHEADチェックで重複回避、ドキュメントはfrontmatterのgrowi_pathで一意特定

- **CodingAgent前提の段階移行プラン**
    - 「各PhaseはCodingAgentが1つのまとまった変更として実装・検証・ドキュメント更新まで完結できる粒度にする」
    - 人間が Phase を設計し（Judgment）、AI が各 Phase を実装する（Reckoning）

### 効果

- 仕様ドキュメントをGit管理（現在193ファイル規模）
- 仕様をコードからAIに生成させる → **その過程で見つかったバグもある**（SSOTの恩恵）
    - AI「コードからするとこの仕様です」→ 人間「マジ？それバグじゃん…コードを直して？」
- コミット履歴で誰がやってくれたかわかる（感謝を伝えやすい）
- 重い仕様はPRして認識合わせできる（普段の変更は直PUSH）

### ここで起きていたこと

- 「何を自動化するか」「どう設計するか」の枠組みは人間が決め、「ツール構築」「同期実行」はAIに演算させた
- Claude Codeでサクッと作れた。ツールに問題があって移行できない → これもAIで解決
- 「時間がない」で届かなかった仕組みづくりに手が届いた
- ミニアプリケーション作成みたいな感覚 — どんな機能が必要か、制約は何か、トレードオフは何か。アプリケーション作成の一連を素早く体験できた

## 事例2: AIレビューワークフロー — 「判断を構造化し、育てる」

> 趣旨: チームのメンタルモデルの洗練を重視し、人間に求められる判断力を身につけられる仕組みを作ろう

### 課題 — なぜ作ろうと思ったか

- BEのコアメンバーが別チームに引き抜かれた → PdM1名・BE/FE1名（私）・FE2名体制に
- コード自体はAIで早く完成するが、**レビューコストが高くなっていた**

- **AIにレビューさせるだけでは不十分:**
    - 確認してほしいことを確認してくれるとは限らない（AIは確率的出力なのでガードレールが必要）
    - バグ探しをレビューの主目的にすると、テスト / Lint / 静的解析と責務が競合する
    - AI生成コードは速度だけが上がり、人間の理解速度は変わらない → 「誰も十分に説明できないコード」が蓄積する
    - 個人の成長につながらない（AIに言われたからそうしました、では何も身につかない）
    - チームの成長につながらない

- レビューには**2つの時間軸**がある
    - 短期: この変更をいま組み込むべきかを判断する
    - 長期: その判断を担える人を増やす
    - 単発のレビューコメントで教育を主目的化すると、採否判断の場が重くなる
    - しかしレビュー制度全体で教育を副次化すると、Judgment を担える人が増えない

- コードレビューの本質は、「コードベースが持続的に成長し続ける」ことを保証すること
    - つまり「この変更を自分たちのプロダクトに組み込むべきか」を判断する場
    - バグ発見は副次的価値であり、核心は**メンタルモデルの共有**
    - 教育も、単発のレビューコメントでは副次だが、レビュー制度全体では中心課題になる
    - 教育は「教えること」より「判断に参加させること」で達成される
    - そのためにはメンバーの**メンタルモデル**を強化する必要がある
        - 設計: どのような**取捨選択**をして今のコードに至るのか
        - 仕様: どのような機能が存在し、どのような機能が**無い**のか
        - トレードオフ: 何を捨てて何を採ったのか
        - 影響範囲: この変更がどこまで波及するのか

### 判断: どう設計するか決める（Judgment）

- **「AIがチェックし、人間が採否を判断する」ワークフローの設計** ← これが「問い」
- **著者が先に自分のメンタルモデルへ統合してからレビューに出す** ← これを仕組みに埋め込む
    - 「AIが書いたので詳細はよく分からないが、テストは通っている」はレビューに出せない状態
    - レビュー前に、コード・設計意図・トレードオフ・影響範囲を自分の言葉で説明できる状態にする
- **レビュー制度として Judgment を育てる** ← これも同時に満たす
    - 著者は「自分は何を採るのか」を明示する
    - レビュワーは「その判断は妥当か」を問う
    - 教育的な長文講評ではなく、判断への参加を訓練機会にする

- セルフレビュー（著者用）とピアレビュー（レビュワー用）を分離

|  | セルフレビュー | ピアレビュー |
|---|---|---|
| **利用者** | PR著者 | レビュワー |
| **目的** | 網羅的チェック + **意思決定の記録** | PR理解 + 重要な指摘のみ質問形式 |
| **エージェント数** | 全6〜9 | 最小2〜最大9 |
| **トーン** | 指摘（断定的） | 質問（対話的） |
| **成果物** | 修正アイテム + 意思決定記録 | コメント候補 + 判断確認の質問 |
| **長期的役割** | 自分の判断を言語化する訓練 | 他者の判断を検証する訓練 |

- PRで共有すべき4要素を明示
    - コード（差分そのもの）
    - 設計意図（なぜこの構造か）
    - トレードオフ（何を捨てて何を採ったか）
    - 影響範囲（どこに波及するか）
    - `/diff-navigator` と `/draft-pr` は、この4要素を埋めるための補助として設計

- 意思決定フェーズの設計（セルフレビューの核心）
    - 各findingに対して著者が必ず判断を下す:
        - ✅ 修正する / 💬 現状維持（理由を記録） / 📋 別issueにする / 🚫 棄却する
    - この記録がPR本文に埋め込まれ、ピアレビュー時に参照される
    - 検討済みの観点はレビュワーに再指摘されない → レビュワーは未検討の論点だけに集中
    - 重要なのは、著者が「AIに言われたから」ではなく「自分はこう判断した」と記録すること

- 9専門エージェントの設計

| 区分 | エージェント | スコープ |
|------|-------------|---------|
| FE/BE分離 | bug-hunter, security, performance × FE/BE | 各技術スタックのみ |
| クロスカッティング | architecture, simplicity, spec | 全差分 |

#### エージェントの動かし方

各エージェントには **Role → Scope → Task → Constraints → Context → Output** の構造化プロンプトが渡される。

```
Role:        "You are a specialist in {CATEGORY}"
Scope:       レビュー対象のファイルリスト（FE/BEでスコープ）
Task:        差分を読み、新たに導入された問題を発見する
Constraints: Read-only、自分の専門領域のみ、コードに基づく推論のみ
Context:     仕様情報、技術スタック、ブランチ情報、コミットログ、差分
Output:      JSON配列 [{ severity, category, file, line, title, description, suggestion, confidence }]
```

- エージェントはコードを変更できない（Read-only: Bash, Read, Grep, Glob のみ）
- 各エージェントは自分の専門外については何も言わない → 他のエージェントが担当

#### スキル間のデータの流れ

```
/self-review ──→ .claude/reviews/self-review-*.md（意思決定記録）
                        │
                        ↓
/draft-pr ───→ PR本文に意思決定記録と設計意図を埋め込む
                  <!-- peer-review時に参照されます -->
                        │
                        ↓
/peer-review ──→ セルフレビュー記録を読み取り
                  ✅ 修正済み → スキップ
                  💬 現状維持 → 理由を確認、必要なら質問
                  🚫 棄却 → 妥当性を検証
                        │
                        ↓
/post-review ──→ GitHub PR に Pending レビューとして投稿
                  （手動Submitまで公開されない）
```

#### ワークフロー全体像

```
┌─ PR著者 ─────────────────────────────────────────┐
│ 1. 開発・コミット                                  │
│      ↓                                            │
│ 2. /self-review ← 全エージェントで網羅的チェック    │
│      ↓              （= Reckoning）                │
│ 3. 意思決定フェーズ ← 各findingに判断を下す          │
│      ↓              （= Judgment）                 │
│ 4. /draft-pr ← 意思決定記録をPR本文に反映           │
│      ↓                                            │
│ 5. レビュー依頼                                    │
└──────┬────────────────────────────────────────────┘
       ↓
┌─ レビュワー ─────────────────────────────────────┐
│ 6. /peer-review ← 検討済み事項を自動スキップ        │
│      ↓              （= Reckoning）                │
│ 7. コメント対象を選択 ← 対話的フィルタリング         │
│      ↓              （= Judgment）                 │
│ 8. /post-review ← GitHub PRにPendingレビュー投稿   │
└──────────────────────────────────────────────────┘
```

- 各ステップに「演算（AI）で候補を広く出し、判断（人間）で採否を決める」ループが埋め込まれている
- 差分サイズに応じたTier戦略（〜1000行: そのまま / 1000-3000: FE/BE分割 / 3000+: 要約+個別読取）
- PR本文には差分だけでなく、設計意図・トレードオフ・影響範囲を載せる
    - レビュアーは「何が変わったか」だけでなく、「なぜそれを採るのか」を判断できる

### 効果

- 手順が定まっているので、レビュー観点を言語化していくことで品質が確保できるようになる
    - 観点の大量チェックは人間がやると形骸化する → AIで解決
- テスト / Lint / 静的解析とレビューの責務を分離しやすくなった
    - 自動化可能な欠陥検出は前段に寄せ、レビューでは設計意図・トレードオフ・影響範囲に集中できる
- PR著者がAI生成コードを読み直し、意思決定を記録してから出すので、ブラックボックスな変更が減る
- 単発のレビューコメントは軽く保ちながら、レビュー制度全体としては Judgment の訓練機会を増やせる
- レビュアーのコメントが「教えるためのコメント」ではなく「判断確認の質問」に寄ってくる
    - 学びは説教ではなく、判断への参加として発生する
- **Issueから始める動機が生まれた** — Issue を充実させようという動機、チームですり合わせようという動機
    - 実装自体もIssue起点にするようになってきた
    - Issueをチームですり合わせすれば実装前に方向性を合わせられる

### ここで起きていたこと

- 「何をチェックするか」「指摘にどう対応するか」を人間が判断し、「網羅的チェック」「出力検証」をAIに演算させた
- 意思決定を記録として構造化することで、レビューが「問題を見つける」作業から「この変更を組み込むべきかを判断し合う」対話に変わった
- AIは観点列挙と要約を担い、最終的なチェックポイントは人間同士のレビューに残した
- 教育をレビューコメントの量に埋め込むのではなく、判断プロセスへの参加として設計した

## 2つの事例が示すパターン

### 判断と演算の分離が繰り返されている

| | 判断（Judgment） | 演算（Reckoning） |
|---|---|---|
| ドキュメントパイプライン | 何を自動化するか、どう設計するか | ツール構築、自動同期 |
| レビューワークフロー | この変更を組み込むべきか、どの判断を採るか | エージェントによる網羅的分析、要約、観点別チェック |
| 共通 | 問いを立てる、採否を決める、責任を持つ | 与えられた文脈で広く計算し、候補を出す |

- 事例1は「成果物の作り方」を設計し、事例2は「判断の仕方」を構造化した
- どちらも人間が枠組みと採否を決め、AIがその範囲で実行する — このループが繰り返されている
- 事例2では、コードレビューを「バグ探し」ではなく「判断共有と判断育成のインフラ」として再設計した

### レビューでは「場」と「制度」を分けて考える

- レビューの**場**の主目的は、その変更を組み込むかどうかの判断
- レビューの**制度**の主目的には、その判断を担える人を増やすことを含めるべき
- だから教育は、単発レビューでは副次、制度設計では中心課題になる
- AI時代には Reckoning を外部化できる分、この制度設計の重要性はむしろ上がる

### 「問い」の質がすべてを決める

- 適切なコンテキストを提供すれば、AIは特定の演算タスクでは人間以上の速度・網羅性を発揮する
    - 本当に？と思われる方は以下のモデルを使ってみよう
        - Claude Opus 4.6 high
        - GPT 4.5 xhigh
- 立てた問いが明確であれば、AIは人間より速く、条件によってはより網羅的な出力を返してくれる
- **ただしコンテキストの提供自体に能力が必要**
    - 言語化力・問いを立てる力・何を決めたいかを決める力
    - ここでは LLM を、自然言語を入力・出力とする強力な計算機として扱う
- **「問い」の質は md ファイルや SKILL に現れる**
    - ドキュメントパイプライン: meta/ のドキュメント群 = 判断基準の言語化
    - レビューワークフロー: SKILL.md, agent-prompt.md = チェック観点と採否基準の言語化
    - 言語化しなければ、AIにコンテキストとして渡すことはできない

## 結び: 人間が引き受けるべきこと

### 「何を問うか」を引き受けるのは人間

- 言語化以前に**違和感**が必要（直感を磨く必要がある）
- 何を解決すれば十分か、どのトレードオフを受け入れるかを決めるのは人間
    - 単に「開発フローにおける一般的な課題を出力して」と言うだけなら、それはAIにもできる
- コードレビューに出す前に、その変更を自分のメンタルモデルに統合する責任も人間が負う
    - AIが書いたコードでも、自分の言葉で設計意図・トレードオフ・影響範囲を説明できなければならない
- もし漏れている観点があれば、そもそも立てた「問い」や評価軸が悪い可能性がある

### 問いを立てる能力は開発の中で育てる

- 今までは若手に演算（労力のかかる仕事）を移譲し、手触りを通じて成長できた
    - 成長とは: 具体的行動の繰り返しで現実と自身の世界の摩擦を実感し、言語化以前の判断力を養うこと
    - シニアは違和感・直感が先にあり、それはなぜかという言語化が後から来る
    - 短い思考に多くの情報を詰められるようになる（「冪等性」というワードの含意のように）
- AIが演算を代替する時代、**個人の成長をどう支えるか**は設計すべき課題
    - 個人の努力に任せるのは酷
    - HITLは時代遅れではない — 能力拡張が必要な場面では人間がループに入るべき
    - 良いモデリングは触りながら理解する中でしか生まれない
    - レビューは、そのループに人を参加させる数少ない制度的な場になる
    - だから積極的に判断→演算のループの中に入る

### 教育をどこに置くか

- レビューコメントの主目的は教育ではない
    - その場では、変更を採るかどうかの判断が最優先
- しかしレビュー制度の目的には、Judgment の育成を明示的に含めるべき
    - AIが Reckoning を代替するほど、人間に残る希少資源は Judgment になる
- 教育は「丁寧に教えること」より「判断に参加させること」で起こる
    - 著者に判断を書かせ、レビュワーにその妥当性を問わせる
    - 正解の伝達ではなく、判断の比較と更新を回す

### あるべき姿

- **何を決めるかは人間が担い、計算可能な部分をAIに委ねる**
    - 決定→演算→決定→演算のループ
    - 「理解」するためのスピードを上げる。AIに言語化を補助させる。判断の材料を広く出させる。
    - 良い問いを立てるためには、理解することを避けられない — だから積極的にループの中に入ろう
- レビューは不要になるのではなく、むしろ Judgment の比重が上がる
    - テストが「意図通り動くか」を担い、レビューは「組み込むべきか」を担う
    - さらにレビュー制度は「将来その判断を担える人を増やせるか」も担う
    - 責任を人間が取る以上、レビューのチェックポイントは残る
- Smithが言うように、少なくとも現行のAIにおいて **演算（Reckoning）は判断（Judgment）を代替できない**
    - だからこそ、判断の質を高める仕組みを設計し、演算を委ねることで、人間の能力を最大化する
- **言語化は Judgment を支える重要な実践である**
